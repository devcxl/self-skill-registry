# 业务示例

## 支付系统

### 业务目标分层

```text
核心：支付状态流转、幂等、退款、对账
支撑：商户管理、通知配置
通用：登录、文件上传、字典管理
```

只有核心业务值得重点使用 DDD。

### 事件风暴

```text
用户提交订单
→ 订单已创建
→ 发起支付
→ 支付渠道受理
→ 支付成功
→ 订单已支付
→ 发放权益
```

### 限界上下文

```text
订单上下文
支付上下文
库存上下文
履约上下文
会员上下文
营销上下文
```

不同上下文的同名概念不应合并：

```text
订单状态：待支付、已支付、已取消
支付状态：处理中、成功、失败、已退款
```

订单和支付不是同一个模型，不要用一张状态表强行统一。

### 统一语言

```text
支付单：平台内部的一次支付请求
渠道交易：第三方支付渠道产生的交易
支付成功：平台已经确认渠道资金处理成功
订单已支付：订单上下文接受支付结果后的业务状态
```

### 聚合

订单聚合：

```text
Order
├── OrderItem
├── OrderAmount
└── OrderStatus
```

订单聚合负责：

```java
order.cancel();
order.confirmPayment(paymentId);
order.changeReceiver(receiver);
```

不要把用户、订单、支付、库存全部放进一个大聚合。

### 上下文协作

```text
支付上下文
    发布 PaymentSucceeded

订单上下文
    消费 PaymentSucceeded
    调用 order.confirmPayment()

履约上下文
    消费 OrderPaid
    创建履约任务
```

不要让支付服务直接修改订单表。

## 电商系统

### 限界上下文划分

```text
订单上下文
支付上下文
库存上下文
履约上下文
会员上下文
营销上下文
```

### 判断是否拆分的标准

- 订单状态：待支付、已支付、已取消
- 支付状态：处理中、成功、失败、已退款

这两组状态分别属于不同的有界上下文，有不同的生命周期和业务规则，不应合并。
