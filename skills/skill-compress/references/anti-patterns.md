# Skill 压缩反模式

下面列出常见的 skill 膨胀问题，以及应对方式。

## 1. 万能型 description

### 反模式

```yaml
name: engineering-helper
description: 用于处理各种软件工程相关任务，包括设计、开发、调试、重构、部署等。
```

### 问题
- 触发边界过宽
- 容易误命中相邻任务
- 不能体现 skill 的单一职责

### 建议
改成明确的任务边界：

```yaml
description: 用于生成 Spring Boot 多模块骨架。当需要新建标准模块或补齐固定分层目录时触发；不要用于业务实现、SQL 优化或架构评审。
```

---

## 2. 正文写成教程而不是协议

### 反模式
正文开头先讲背景、再讲理念、再讲历史原因，真正的执行步骤很少。

### 问题
- 加载成本高
- 关键步骤被淹没
- 模型难以快速抽取执行协议

### 建议
正文只保留：
- 作用
- 适用 / 不适用
- 输入
- 执行步骤
- 输出要求
- 约束

---

## 3. 示例堆积

### 反模式
为了说明一个规则，连续放 4 到 8 个相似示例。

### 问题
- 正文变长
- 规则与例子比例失衡
- 后续维护困难

### 建议
同类示例只保留 1 个，其他放到 `references/`。

---

## 4. 一个 skill 承担多个流程

### 反模式
同一个 skill 同时做：
- analyze
- generate
- review
- fix

### 问题
- 输入输出不统一
- 触发条件过宽
- 模型容易在错误阶段使用 skill

### 建议
拆分为：
- `xxx-analyze`
- `xxx-generate`
- `xxx-review`
- `xxx-fix`

---

## 5. 约束散落在长段说明中

### 反模式
重要约束埋在长段自然语言里，缺少清晰条目。

### 问题
- 约束不易执行
- 容易被忽略

### 建议
改为硬规则清单，例如：

```md
## 约束
- 不新增未要求依赖
- 不修改无关文件
- 保持现有命名风格
```

---

## 6. 把外部资料硬塞进 SKILL.md

### 反模式
将长模板、命令列表、背景附录、FAQ 全部放入主文件。

### 问题
- 主文件体积过大
- 结构失衡
- 更新代价高

### 建议
迁移到：
- `references/`
- `assets/`
- `scripts/`

主文件只保留“何时使用这些资料”的说明。
